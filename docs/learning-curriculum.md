## Part 0 — Foundations

These are the building blocks underneath everything else. Skip if comfortable.

### 0.1 Transformer architecture (decoder-only LLM)

**What it is.** A stack of identical layers. Each layer has two subblocks: **self-attention** (tokens look at other tokens to update their representations) and a **feed-forward network / MLP** (each token is independently transformed by a 2-layer MLP). A residual stream carries the running representation; each subblock reads from it and writes back to it.

**Where each subblock's weights live (a Qwen-style decoder layer):**
- Attention: `q_proj`, `k_proj`, `v_proj` (project residual stream → queries, keys, values), `o_proj` (project attention output back)
- MLP: `gate_proj`, `up_proj` (project to 4×-wide hidden), `down_proj` (project back)

**Why this matters here.** Our voice LoRA targets **only the attention projections** because of where style vs knowledge are stored — see §1.4.

**Read.**
- "Attention Is All You Need," Vaswani et al., arXiv:1706.03762 (the original)
- Anthropic Transformer Circuits walkthrough — <https://transformer-circuits.pub/2021/framework/index.html>
- 3Blue1Brown's chapter on attention (intuition) — <https://www.youtube.com/watch?v=eMlx5fFNoYc>

### 0.2 Where knowledge lives in transformer weights

**What it is.** Empirical interpretability finding: **factual associations are stored in the mid-layer MLPs** as key-value lookups. The `up_proj` rows act as keys; the `down_proj` columns act as values. Specific facts can be surgically edited by modifying a small number of rows.

**Why this matters here.** It directly justifies our LoRA target choice. If facts live in MLPs and we want to teach voice without rewriting facts, we leave MLPs untouched and only adapt attention.

**Read.**
- ROME — "Locating and Editing Factual Associations in GPT," Meng et al., arXiv:2202.05262
- MEMIT — "Mass-Editing Memory in a Transformer," Meng et al., arXiv:2210.07229
- Geva et al., "Transformer Feed-Forward Layers Are Key-Value Memories," arXiv:2012.14913
- Rimsky et al., "Steering Llama 2 via Contrastive Activation Addition," arXiv:2312.06681 (style/persona directions)

### 0.3 Embeddings and cosine similarity

**What it is.** An embedding model maps text → a fixed-length vector in **R^d** (d = 768, 1024, 1536 typical). Semantically similar text → vectors with high cosine similarity. Cosine = dot product of unit-normalised vectors, range [-1, 1].

**Math.** `cos(a, b) = (a · b) / (‖a‖ · ‖b‖)`. For unit-norm vectors this is just `a · b`.

**Variables.**
- `d` — embedding dimensionality (more = more expressive, more storage, slower)
- `model` — Voyage, OpenAI text-embedding-3, BGE, Cohere embed-v3
- `normalization` — almost always L2-normalise before indexing

**Where it shows up here.**
- sku-food uses Voyage `voyage-4-lite` at d=1024 with HNSW cosine index (migration 011)
- speaker_id.py: ECAPA-TDNN voice embeddings, cosine-similar to a Peter reference

**Read.**
- MTEB leaderboard (current SOTA embedding models) — <https://huggingface.co/spaces/mteb/leaderboard>
- Voyage docs — <https://docs.voyageai.com/embeddings>

### 0.4 Vector indexes: HNSW

**What it is.** **H**ierarchical **N**avigable **S**mall **W**orld graphs — an approximate nearest-neighbour structure that lets you query "top-k similar vectors" in `O(log N)` instead of brute-force `O(N)`. Used by pgvector, FAISS, Qdrant, Chroma.

**Variables.**
- `M` — max connections per node (16–64; higher = better recall, more RAM)
- `ef_construction` — search width at build time (200–400)
- `ef_search` — search width at query time (100–500). **Single biggest recall-latency knob.**

**Where it shows up here.** `supabase/migrations/004_chunks.sql` creates an HNSW index. `supabase/migrations/016_hybrid_search.sql` does `SET LOCAL hnsw.ef_search = 100;`.

**Read.**
- Malkov & Yashunin, "Efficient and robust approximate nearest neighbor search using HNSW," arXiv:1603.09320

### 0.5 BM25 (sparse / keyword search)

**What it is.** A bag-of-words ranking function. For each query token, score documents by how often the token appears (TF, with diminishing returns) weighted by how rare the token is in the corpus (IDF). The **opposite signal** to dense embeddings: BM25 nails exact terms (SKUs, brand names, jargon); dense embeddings nail semantic synonyms.

**Math (simplified).** `score(q, d) = Σ_{t in q} IDF(t) · TF(t, d) · (k1+1) / (TF(t, d) + k1·(1 - b + b·|d|/avgdl))`. The hyperparams `k1 ≈ 1.2` and `b ≈ 0.75` are near-universal.

**Variables.**
- `k1` — term frequency saturation (low = saturate fast)
- `b` — document-length normalisation
- The **tokeniser / analyzer** (stemming, stopwords, lowercasing) — bigger effect than k1/b

**Where it shows up here.** sku-food uses Postgres `tsvector` + `websearch_to_tsquery` (effectively BM25 over English stemmed tokens) — see migration 014 + the `sparse` CTE in migration 016.

**Read.**
- Robertson & Zaragoza, "The Probabilistic Relevance Framework: BM25 and Beyond" — <https://www.staff.city.ac.uk/~sbrp622/papers/foundations_bm25_review.pdf>
- Postgres FTS docs — <https://www.postgresql.org/docs/current/textsearch.html>

### 0.6 Reciprocal Rank Fusion (RRF)

**What it is.** A way to combine multiple ranked lists into one. For each item, sum `1/(k + rank_i)` across every list it appears in. **No score calibration needed** — works on ranks only, which makes it brittle-free across heterogeneous scorers (dense cosine, BM25, reranker, etc).

**Math.** `RRF(d) = Σ_i (w_i / (k + rank_i(d)))`. The `k=60` constant is the standard default (smooths out top-rank dominance). Weights `w_i` let you bias the fusion — Anthropic recommends **4:1 dense:sparse** for contextualised RAG.

**Variables.**
- `k` — rank smoothing constant (lower = top ranks dominate more)
- `w_i` per list — relative trust in each retriever

**Where it shows up here.** `supabase/migrations/016_hybrid_search.sql` line `(COALESCE(4.0 / (60 + d.dense_rank), 0) + COALESCE(1.0 / (60 + s.sparse_rank), 0))` is RRF with 4:1 dense:sparse.

**Read.**
- Cormack et al., "Reciprocal Rank Fusion outperforms Condorcet and individual rank learning methods" (2009) — <https://dl.acm.org/doi/10.1145/1571941.1572114>

## Part 1 — Fine-Tuning

### 1.1 What "fine-tuning" actually does

**What it is.** Take a pretrained model and continue training on a smaller dataset to shift its behaviour. **Full fine-tune** = update all parameters (expensive, prone to catastrophic forgetting). **Parameter-efficient fine-tuning (PEFT)** = freeze the base and add a small number of trainable parameters (LoRA, prompt tuning, adapters, IA³).

**Modes.**
- **Pretraining** — next-token prediction on raw text, billions of tokens, no labels
- **SFT (Supervised Fine-Tuning)** — labelled (prompt, completion) pairs, standard cross-entropy loss
- **Preference optimization** — DPO/ORPO/KTO/SimPO — push model toward "preferred" outputs (see 1.5)

**Where it shows up here.** Our voice fine-tune is **LoRA-based SFT** of Qwen 3.5 9B.

### 1.2 LoRA — Low-Rank Adaptation

**What it is.** Instead of training a full d×d weight matrix `ΔW`, decompose the delta as `A·B` where `A` is d×r and `B` is r×d for some small rank `r` (often 4–64). Train only A and B; freeze base W. At inference the model uses `W + (alpha/r)·A·B`.

**Math.** Effective weight: `W_eff = W + (alpha/r) · A · B`. Parameter count drops from `d²` to `2·d·r`. For d=4096, r=16: 16M → 131k params per matrix. Negligible compared to the frozen 7-9B base.

**Variables.**
- `r` (rank) — adapter capacity. Low (4–8) = conservative style nudges; high (32–128) = bigger behavior shifts and more risk of overwriting base knowledge
- `alpha` — scaling. Effective scale = `alpha/r`. Common convention: `alpha = 2·r`. We use `alpha = r` (scale = 1.0) for the gentlest possible nudge
- `target_modules` — **which** weight matrices to adapt. Attention only (q, k, v, o) vs all-linear vs MLP-only. See §1.3
- `dropout` — typically 0.05
- `learning_rate` — typically 1e-4 to 1e-5; cosine schedule
- `bias` — usually `"none"`; sometimes `"lora_only"`

**Where it shows up here.** `docs/research-voice-rag-pivot.md` §4. Run 003 starting point: r=16, alpha=16, target = attention only, 1–2 epochs, LR 5e-5.

**Read.**
- Hu et al., "LoRA: Low-Rank Adaptation of Large Language Models," arXiv:2106.09685 (the original)
- Biderman et al., "LoRA Learns Less and Forgets Less," arXiv:2405.09673 (when LoRA wins/loses vs full FT)
- Liu et al., "DoRA: Weight-Decomposed Low-Rank Adaptation," arXiv:2402.09353 (LoRA upgrade that decomposes magnitude + direction)
- Hugging Face PEFT docs — <https://huggingface.co/docs/peft>

### 1.3 QLoRA — 4-bit quantization + LoRA

**What it is.** Load the frozen base weights in **4-bit NF4 (NormalFloat-4)** instead of 16-bit, then train LoRA adapters on top. Cuts VRAM ~4×, lets you fine-tune 7-9B models on a single 24GB GPU.

**Variables.**
- `bnb_4bit_quant_type` — `nf4` (recommended) or `fp4`
- `bnb_4bit_compute_dtype` — typically `bfloat16` (compute happens in 16-bit even though storage is 4-bit)
- `bnb_4bit_use_double_quant` — quantize the quantization constants too (saves another ~0.4 bits per param)

**Where it shows up here.** `pyproject.toml` has `bitsandbytes>=0.43`. The Unsloth trainer uses QLoRA by default.

**Read.**
- Dettmers et al., "QLoRA: Efficient Finetuning of Quantized LLMs," arXiv:2305.14314
- Unsloth — <https://github.com/unslothai/unsloth>

### 1.4 Where style vs facts live → why attention-only LoRA

**The empirical claim.** Facts → MLPs (mid-layer key-value memories, per MEMIT / ROME / Geva). Style/persona/register/role-playing → **attention output projections and mid-to-late layer attention patterns** (per Rimsky et al., Anthropic's persona-feature work in "Scaling Monosemanticity").

**Practical consequence.** If you adapt MLPs (especially `up_proj`/`down_proj`), you compete with stored facts → model hallucinates, contradicts retrieved RAG context, forgets capabilities (the Run 001/002 failure). If you adapt only attention (q/k/v/o), you shape **how** the model attends to tokens and routes information — which is what "voice" mostly is — without touching where world-knowledge is stored.

**Where it shows up here.** The single most important architectural commitment of this whole project. `docs/research-voice-rag-pivot.md` §4. We also explained it in detail in the conversation transcript.

**Read.**
- Geva et al., arXiv:2012.14913 (MLPs as memories)
- Meng et al., arXiv:2202.05262 (ROME) and arXiv:2210.07229 (MEMIT)
- Rimsky et al., arXiv:2312.06681 (steering via attention contrast)
- Anthropic, "Scaling Monosemanticity" — <https://transformer-circuits.pub/2024/scaling-monosemanticity/index.html>
- Biderman et al., arXiv:2405.09673 (attention-only LoRA forgets less)

### 1.5 Preference optimization — DPO, ORPO, KTO, SimPO

These are post-SFT (or unified with SFT) methods that push the model toward "preferred" outputs over "rejected" ones. SFT teaches what to say; preference optimization teaches what **not** to say.

**DPO** — Direct Preference Optimization. Given (prompt, chosen, rejected) triples, train a classifier-style loss that increases the log-probability ratio of chosen vs rejected, regularised by a KL penalty to a reference (the SFT model). No separate reward model needed.
- **Variables**: `beta` (KL strength; lower = freer policy)
- **Risk**: tends to over-shift on surface markers; can degrade general reasoning
- **Read**: Rafailov et al., arXiv:2305.18290

**ORPO** — Odd Ratio Preference Optimization. Folds preference learning into the SFT loss in a single stage. No reference model, no separate DPO pass. Specifically reported to work well for stylistic preferences.
- **Variables**: `beta` (odds-ratio weight on the preference term)
- **Why we chose ORPO over DPO if we polish**: cheaper, monolithic, better for low-data style
- **Read**: Hong et al., arXiv:2403.07691

**KTO** — Kahneman-Tversky Optimization. Works on **unpaired** binary labels (thumbs up/down) instead of pairs. Useful when you only have rater signal, not preference pairs.
- **Read**: Ethayarajh et al., arXiv:2402.01306

**SimPO** — Simple Preference Optimization. Reference-free DPO variant. Simpler but length-biased; less proven for persona.
- **Read**: Meng et al., arXiv:2405.14734

**Where it shows up here.** §4 of the research synthesis: "SFT primary, optional ORPO polish only if SFT leaves measurable style gaps."

### 1.6 NEFTune — noisy embeddings during fine-tuning

**What it is.** Add a small uniform-random perturbation to the embedding layer's output during training. Improves instruction-following without changing any architecture. Free win on most SFT recipes.

**Variables.**
- `neftune_noise_alpha` — magnitude of the perturbation. 5 is the usual default.

**Where it shows up here.** §4 LoRA starting point includes `neftune_noise_alpha=5`.

**Read.** Jain et al., "NEFTune: Noisy Embeddings Improve Instruction Finetuning," arXiv:2310.05914.

### 1.7 Catastrophic forgetting and mitigations

**What it is.** Training on a narrow dataset causes the model to lose general capabilities it had before. Classical neural-net problem; particularly visible when LoRA rank or training duration is too high.

**Mitigations (priority-ordered).**
1. **Low rank + attention-only targets** (the structural fix)
2. **Replay** — 5–10% of batches from a generic instruction set (Alpaca-cleaned, OpenHermes subset) to anchor general capability
3. **KL-to-base or L2-on-deltas regulariser** — penalise large deviations from the pretrained model (sometimes called "LoRA-FA" or "anchored LoRA")
4. **Short training** — 1–2 epochs, eval-driven stopping
5. **Freeze embeddings + lm_head**

**Read.** Biderman et al., arXiv:2405.09673 explicitly studies this for LoRA. Original notion: McCloskey & Cohen 1989 (catastrophic interference).

### 1.8 Persona / character / role-playing fine-tuning

**What it is.** A subfield of style-fine-tuning focused on building agents that play specific personas (historical figure, fictional character, brand voice).

**Key trick.** Always train **and** infer with the same explicit `<system>` header defining the persona AND a `<context>` block for retrieved evidence (often empty during voice-only training). This teaches the model "facts come from the block, voice comes from the persona slot" — the structural separation is what stops the adapter from absorbing facts as the persona's identity.

**Where it shows up here.** §4 data format recommendation. Same wrapper at train and inference time.

**Read.**
- Shao et al., "Character-LLM: A Trainable Agent for Role-Playing," arXiv:2310.10158 (foundational)
- Wang et al., "RoleLLM," arXiv:2310.00746
- Samuel et al., "PersonaGym: Evaluating Persona Agents and LLMs," arXiv:2407.18416 (eval rubric we borrowed)

### 1.9 Synthetic data generation for instruction tuning

**Why we need it.** Most of Peter's audio is monologue, not Q&A. We need (instruction, response) pairs to SFT-train. Three approaches:

1. **Self-Instruct** — seed an LLM with a small handcrafted instruction set, ask it to generate more instructions, filter for quality. Wang et al., arXiv:2212.10560.
2. **Evol-Instruct** — iteratively make instructions harder/more diverse via prompting (used by WizardLM). Xu et al., arXiv:2304.12244.
3. **Instruction backtranslation ("Humpback") / LongForm** — *reverse* the problem: given a corpus of high-quality text, ask an LLM "what question would have produced this text?" Then train on the synthesised (question, original-text) pairs. The original text is the gold — so the model learns from real prose, not LLM prose. Best fit for our podcast-monologue case.
   - Li et al., "Self-Alignment with Instruction Backtranslation" (Humpback), arXiv:2308.06259
   - Köksal et al., "LongForm," arXiv:2304.08460

**Where it shows up here.** §5 of the research synthesis describes the reverse-Q&A pass we'll add in Phase 2. The schema field `generation_mode = "reverse_qa"` is wired through.

### 1.10 Style transfer evaluation

**Stylometry** — quantitative measures of writing style. Function-word distributions, type-token ratio, sentence length, clause depth, LIWC categories. These are model-free and reproducible.

**Authorship verification classifier** — train a small DistilRoBERTa to discriminate Peter vs other Canadian food-retail writers. Report `P(Peter)` on every output. This is the canonical evaluation pattern in style-transfer literature.

**LLM-as-judge** — prompt a strong LLM (Claude Sonnet 4.7) with a rubric and pairwise A/B outputs. Cheap, scalable, biased — always pair with stylometric and human eval.

**Where it shows up here.** §8 of the research synthesis. Release gate: `P(Peter) ≥ 0.75 under RAG load`.

**Read.**
- LIWC (Linguistic Inquiry and Word Count) — <https://www.liwc.app/>
- StyleBench-style work, e.g., Krishna et al., "Reformulating Unsupervised Style Transfer as Paraphrase Generation," arXiv:2010.05700

## Part 2 — Retrieval-Augmented Generation (RAG)

### 2.1 Vanilla RAG (the minimum viable pattern)

**What it is.** At query time: embed the user query → retrieve top-k similar chunks from a vector store → concatenate them into the LLM prompt → generate. The retrieved chunks ground the LLM's answer in your data.

**Why use it.** (a) Cheaper than long-context for large corpora. (b) Up-to-date — change a chunk, the answer changes, no retraining. (c) Cite-able — you know which chunks were retrieved. (d) Avoids cramming knowledge into weights (the Run 001/002 anti-pattern).

**Variables.** Embedding model, chunk size, top-k, similarity threshold, prompt structure.

**Where it shows up here.** sku-food at its simplest is this — except it adds hybrid + rerank + reordering on top.

### 2.2 Contextual Retrieval (Anthropic, Sept 2024)

**What it is.** Before embedding each chunk, prepend a short (50–100 token) LLM-generated context that situates the chunk within its parent document. Then embed the **contextualised** chunk. Solves the "isolated chunk has no context" failure mode — e.g., a chunk that says "the net wt is 12 oz, 4 servings" is meaningless without knowing which product. With the context prefix, it becomes "Discussion of the new SKU 'Premium Yogurt Cup'. The net wt is 12 oz, 4 servings."

**Numbers (from Anthropic).** ~49% reduction in retrieval failures from the prefix alone; ~67% with reranker added.

**Variables.** Prefix length, prefixing prompt template, the LLM that generates the prefix (Haiku is plenty), whether to also prefix the BM25-indexed version (yes).

**Where it shows up here.** Documented gap to add to sku-food in §6 of the research synthesis. Currently sku-food embeds raw chunks; we can add a prefixing step at ingest time.

**Read.** Anthropic, "Contextual Retrieval" — <https://www.anthropic.com/news/contextual-retrieval>.

### 2.3 Chunking strategies

The unit you embed and retrieve. Bigger = more context, fewer chunks; smaller = more focused matches.

**Fixed-size** — N tokens per chunk with overlap. Simple, lossy.

**Semantic chunking** — split at semantic boundaries (sentence-level embedding distance spikes). Less wasteful, more compute-heavy at ingest.

**Document-aware** — one chunk per row for tabular, one per section for long-form. The right answer for mixed structured+unstructured corpora.

**Late chunking (Jina, 2024)** — embed the whole document with a long-context encoder, **then** pool per chunk. Preserves cross-chunk context. Real win on long narrative docs; modest on tabular.

**RAPTOR (recursive abstractive processing)** — build a hierarchy: chunk → cluster → LLM-summarise cluster → recurse. Retrieval matches the right level of the hierarchy. Useful when "Peter's view on a category" type questions span many chunks.

**Where it shows up here.** sku-food does semantic chunking via `lib/ingestion/chunker.ts`. Newsletters: one chunk per section. Transcripts (us to add): 400-token semantic chunks with timestamp metadata.

**Read.**
- Late chunking — Günther et al., arXiv:2409.04701 + <https://jina.ai/news/late-chunking-in-long-context-embedding-models/>
- RAPTOR — Sarthi et al., arXiv:2401.18059

### 2.4 Reranking with a cross-encoder

**What it is.** Retrieval is fast and approximate (a bi-encoder scores query vs each chunk independently). A **cross-encoder reranker** scores the (query, chunk) pair *together*, attending across both — slower but much more precise. Run on top-K (15–30) retrieval candidates, output top-N (3–8) for the LLM.

**Models.**
- **Voyage `rerank-2.5`** — what sku-food uses
- **Cohere `Rerank 3.5`** — current SOTA managed
- **BGE-reranker-v2-m3** — open-source SOTA
- **ColBERT v2 / PLAID** — late-interaction model, different category; runs at retrieval rather than rerank, very strong but more infra

**Variables.** `top_K` retrieval, `top_N` output, fallback behaviour on rerank API failure.

**Where it shows up here.** `lib/rag/retriever.ts` line 137-150. Top-20 candidates → top-N rerank with `voyageRerank`. Graceful fallback to vector-only on failure.

**Read.**
- Voyage docs — <https://docs.voyageai.com/reranker>
- BGE — Chen et al., arXiv:2402.03216
- ColBERT v2 — Santhanam et al., arXiv:2112.01488

### 2.5 Hybrid search (dense + sparse + RRF)

**What it is.** Run both a dense (vector cosine) retrieval and a sparse (BM25) retrieval in parallel; fuse the two ranked lists with RRF (§0.6). Catches both semantic matches (synonyms, paraphrases) and lexical matches (SKUs, brand names, exact terms).

**Variables.** Dense top-K, sparse top-K, RRF k constant, dense:sparse weight ratio.

**Where it shows up here.** `supabase/migrations/016_hybrid_search.sql` — full Postgres SQL. 4:1 dense:sparse weighting per Anthropic recipe.

### 2.6 Lost-in-the-middle

**What it is.** LLMs attend strongest to the *beginning* and *end* of their context, weakest to the middle. Surprisingly robust effect across Claude, GPT, Gemini.

**Practical fix.** When injecting N retrieved chunks, place the *most relevant* chunk **last** (adjacent to the user message), then descending relevance going up — putting the worst material in the literal middle so it's the least-attended.

**Where it shows up here.** `lib/rag/context.ts` lines 33-36: explicit lost-in-middle reorder.

**Read.** Liu et al., "Lost in the Middle: How Language Models Use Long Contexts," arXiv:2307.03172. Updated 2025 result: NoLiMa benchmark shows long-context degradation past ~32k effective tokens even on frontier models — arXiv:2502.05167.

### 2.7 Advanced RAG patterns we explicitly skipped

**GraphRAG (Microsoft)** — build an entity+relationship graph via LLM extraction across the corpus, summarise communities, retrieve by community. Wins on "what are the themes?" globe-spanning questions. Brutal indexing cost.
- arXiv:2404.16130; <https://github.com/microsoft/graphrag>

**HippoRAG 2** — memory-inspired graph + personalised PageRank retrieval. Cheaper than GraphRAG. Outperforms vanilla on multi-hop benchmarks.
- arXiv:2502.14802

**Self-RAG** — train the model to emit "retrieve" / "reflect" tokens, choosing whether to retrieve and whether the retrieval was useful. Fragile, needs fine-tuned model.
- Asai et al., arXiv:2310.11511

**Corrective RAG (CRAG)** — train a lightweight retrieval evaluator; on low-confidence retrievals, fall back to web search.
- Yan et al., arXiv:2401.15884

**Adaptive RAG** — route queries to different pipelines based on complexity (no-retrieval, single-step, multi-step). Marginal gain vs prompt-based classifier.
- Jeong et al., arXiv:2403.14403

**Why we skipped all of these.** Corpus is moderate-sized and our existing hybrid+rerank stack matches the recommended baseline. Revisit only if eval shows multi-hop or thematic failures.

### 2.8 RAG evaluation

**RAGAS metrics (the canonical four).**
- **Faithfulness** — does the answer make claims that are grounded in the retrieved context? (anti-hallucination)
- **Answer Relevancy** — does the answer actually address the question?
- **Context Precision** — of the retrieved chunks, how many are relevant?
- **Context Recall** — of the relevant facts that *should* have been retrieved, how many were?

**Retrieval-only metrics.**
- **Recall@k** — fraction of relevant docs that appear in top-k
- **MRR@k** (Mean Reciprocal Rank) — `1/rank_of_first_relevant`, averaged across queries

**Where it shows up here.** §8 of the research synthesis: three-layer eval (retrieval, voice fidelity, end-to-end). RAGAS is the daily-driver harness.

**Read.**
- Es et al., "RAGAS: Automated Evaluation of Retrieval Augmented Generation," arXiv:2309.15217
- <https://docs.ragas.io>
- Arize Phoenix (tracing) — <https://docs.arize.com/phoenix>

### 2.9 Citation contract

**What it is.** A documented invariant that `[Source N]` markers in the LLM's output map 1:1 to a specific source in the chip list. Implemented by passing the same ordered source list to the prompt builder AND the chip renderer.

**Where it shows up here.** sku-food `lib/rag/source-order.ts` is the single source of truth; both `assembleContext` and `extractSources` consume it. CLAUDE.md explicitly calls out: "Do not break this invariant."

## Part 3 — Audio Processing Pipeline

### 3.1 Sample rate, channels, codecs (the basics)

**Sample rate.** How many amplitude samples per second. 16 kHz = telephony-grade, plenty for speech; 44.1 kHz = CD; 48 kHz = video standard. ASR models are trained on 16 kHz mono — anything else gets resampled internally.

**Channels.** Mono = 1 channel. Stereo = 2. Speech ASR/diarization treats stereo as the mean of L+R.

**Codecs.** Compression formats. MP3/AAC/Opus are lossy; FLAC/WAV are lossless. PCM = uncompressed samples (what WAV usually contains).

**Where it shows up here.** `downloader.py::_convert_to_pcm_wav` normalises everything to 16 kHz mono PCM wav before any model touches it. `speaker_id.py::_load_wav_mono16k` asserts the rate.

### 3.2 ASR — Whisper architecture

**What it is.** OpenAI Whisper is an encoder-decoder transformer trained on 680k hours of multilingual audio→text. The encoder takes log-mel spectrograms (80-dim, 25ms windows, 10ms stride); the decoder autoregressively generates text tokens conditioned on the audio. "Multitask" — same model does transcription, translation, language ID, voice-activity flagging.

**Models you'll see.**
- `large-v3` — current standard for accuracy
- `large-v3-turbo` — 8× faster, ~1–3% WER regression
- `distil-large-v3` — Hugging Face distillation, 6× faster, English-only

**Variables.**
- `language` — usually `en`; can also `auto-detect`
- `temperature` — 0 for greedy; higher for diversity
- `condition_on_previous_text` — `True` lets context leak between segments (and propagates hallucinations); usually `False` for robustness
- `compression_ratio_threshold` — detects token-repetition hallucinations (default ~2.4)
- `no_speech_threshold` — flag segments as silence above this prob

**Where it shows up here.** `asr.py` wraps WhisperX wrapping faster-whisper.

**Read.**
- Radford et al., "Robust Speech Recognition via Large-Scale Weak Supervision" (Whisper paper), arXiv:2212.04356
- OpenAI repo — <https://github.com/openai/whisper>
- Whisper v3 turbo discussion — <https://github.com/openai/whisper/discussions/2363>

### 3.3 faster-whisper and CTranslate2

**What it is.** A reimplementation of Whisper using **CTranslate2** as inference engine. CT2 is a high-performance C++ runtime for transformer inference — 4–10× faster than vanilla PyTorch Whisper, with optional INT8 quantization on CPU, INT8/FP16 on GPU. **CT2 has no MPS path** — that's why our Apple Silicon execution falls back to CPU.

**Where it shows up here.** `asr.py` uses faster-whisper as the WhisperX backend. `_detect_device` routes MPS to CPU explicitly.

**Read.**
- faster-whisper — <https://github.com/SYSTRAN/faster-whisper>
- CT2 — <https://github.com/OpenNMT/CTranslate2>

### 3.4 Voice Activity Detection (VAD)

**What it is.** Detects which parts of audio contain speech vs silence/noise/music. Used **before** ASR to chunk audio into speech-bearing windows, which (a) speeds up inference (skip silence), (b) prevents Whisper's notorious hallucination on long silent regions ("Thank you for watching", "Subscribe for more").

**Models.** Silero VAD (lightweight, used inside WhisperX), webrtcvad (older, energy-based).

**Where it shows up here.** WhisperX runs Silero VAD automatically. `asr_config.vad_onset` is tunable (0.5 default).

### 3.5 Forced alignment

**What it is.** Whisper's segment timestamps are *interpolated* and drift by hundreds of ms. **Forced alignment** uses a separate model (typically wav2vec 2.0 with CTC head) to produce **word-level** start/end times aligned to the original waveform. This is what gives us per-word confidence scores (`Word.score` in our schema).

**How wav2vec2 forced alignment works.** wav2vec2 outputs a per-frame distribution over phonemes. Given the Whisper transcript, we run **Viterbi decoding** through the lattice constrained to follow the transcript — finding the maximum-probability time-alignment of words to audio frames.

**Where it shows up here.** `asr.py::_ensure_align_model` loads the wav2vec2 model; `whisperx.align` does the Viterbi pass. Per-word `score` flows into `TranscribedSegment.asr_confidence`.

**Read.**
- WhisperX — Bain et al., "WhisperX: Time-Accurate Speech Transcription of Long-Form Audio," arXiv:2303.00747
- wav2vec 2.0 — Baevski et al., arXiv:2006.11477

### 3.6 Speaker diarization

**What it is.** "Who spoke when." Output is a sequence of `(start, end, speaker_label)` turns. Labels are anonymous (`SPEAKER_00`, `SPEAKER_01`) — diarization clusters voices but doesn't know whose voice is whose. That identification is a separate step (§3.7).

**Pipeline (pyannote 3.1, simplified).** (1) segmentation — find speaker-change boundaries; (2) embedding — encode each segment with a speaker-discriminative model; (3) clustering — group embeddings into speakers (agglomerative or spectral).

**Variables.**
- `min_speakers` / `max_speakers` — bound the cluster count
- Embedding model choice (pyannote bundles one)
- Clustering algorithm and threshold

**Where it shows up here.** `diarization.py` wraps the pipeline; CPU-only on Apple Silicon (no MPS support).

**Read.**
- pyannote.audio 3 — Plaquet & Bredin, "Powerset multi-class cross entropy loss for neural speaker diarization," arXiv:2310.13025
- pyannote model card — <https://huggingface.co/pyannote/speaker-diarization-3.1>

### 3.7 Speaker embedding and identification

**What it is.** A model that produces a fixed-length vector for any speech clip such that *clips of the same speaker* cluster close together in cosine distance, *different speakers* are far. The model used for matching diarized clusters to a known person (Peter, in our case).

**ECAPA-TDNN.** Current go-to architecture for speaker embeddings. ECAPA = Emphasized Channel Attention, Propagation and Aggregation; TDNN = Time-Delay Neural Network. Trained on **VoxCeleb** (1M+ utterances, 7k+ speakers).

**Math sketch.** TDNN layers process audio frames with dilated convolutions; channel attention selects discriminative features; statistics pooling collapses to fixed length; final projection to 192-dim embedding. Trained with **AAM-Softmax** (Additive Angular Margin) — pushes same-speaker embeddings into tight angular clusters.

**Where it shows up here.** `speaker_id.py` uses SpeechBrain's `spkrec-ecapa-voxceleb`. Encode the Peter reference once; encode each diarized cluster's centroid (mean of long turns); cosine-compare; threshold (0.55–0.65) decides if a cluster is Peter.

**Read.**
- ECAPA-TDNN — Desplanques et al., arXiv:2005.07143
- SpeechBrain model — <https://huggingface.co/speechbrain/spkrec-ecapa-voxceleb>
- AAM-Softmax — Deng et al., "ArcFace," arXiv:1801.07698

### 3.8 SponsorBlock and ad removal

**What it is.** A community-maintained database of "sponsor segment" timestamps for YouTube videos. yt-dlp can read it directly via the SponsorBlock post-processor.

**Variables.** Categories to mark: `sponsor`, `selfpromo`, `interaction`, `intro`, `outro`, etc.

**Where it shows up here.** `downloader.py::download_youtube` ydl_opts postprocessors include SponsorBlock. `pipeline.py::extract_peter_segments` drops Peter turns inside sponsor spans (≥50% overlap).

## Part 4 — System Composition

### 4.1 Two-stage decoupled architecture

**What it is.** Instead of `retrieve → stuff chunks → voice model generates`, split into `retrieve → small model summarises into a structured fact card → voice model paraphrases the fact card in voice`. The voice model never sees raw chunk prose, so its style isn't flattened by mimicking the retrieved text.

**When to add it.** Only if Stage-1 (single-model RAG) eval shows voice flattening. Default is start with single-model, escalate only on data.

**Where it shows up here.** §7 of the research synthesis. Escalation path, not v1.

**Read.** Anthropic, "Building Effective Agents" (Dec 2024) — Prompt Chaining section. <https://www.anthropic.com/engineering/building-effective-agents>.

### 4.2 Context injection patterns ranked by voice preservation

Three options, increasing voice-preservation:
1. **Worst** — retrieved chunks as a `user` message. Model treats it as input it must respond to in kind.
2. **Middle** — inline `<context>` block in `system` message. Better isolation. (sku-food does this.)
3. **Best** — separate `tool_result` role containing a JSON fact card. Model can't easily clone prose from a JSON list.

**Where it shows up here.** sku-food's `buildSystemMessage` puts `<documents>...</documents>` in the system role — option 2. Option 3 is the upgrade path if voice flattens.

### 4.3 Prompt-engineering rules for voice preservation

- Define identity, voice rules, constraints **before** showing evidence (role-then-evidence ordering)
- Explicit recitation prohibition: "Treat documents as private notes — never quote verbatim, paraphrase only in your voice"
- First-person constraints ("Use 'I', not 'Peter says...'")
- Cite-but-paraphrase contract

**Where it shows up here.** sku-food's `config/projects/skufood/system_prompt.md` already implements all of these. Read it — it's a high-quality reference for persona prompts.

### How to read a paper (since this is most of the work)

For each paper, budget ~2.5 hrs in three passes:

1. **First pass (15 min)** — abstract, intro, conclusion, figures only. Decide whether to continue.
2. **Second pass (45 min)** — full read; skim equations; note unfamiliar terms.
3. **Third pass (60 min)** — re-read with the related concept-index section open; understand every equation.
4. **Notes (30 min)** — write a 1-page summary in your own words. Cite the paper's contribution + what it changed about how you think.

For dense ones (Chinchilla, Whisper, the Transformer Circuits paper) budget 3.5 hrs.

### Daily rhythm

**Weekdays (~3 hrs/day):**
- Morning, 1 hr — videos or book reading (fresh brain)
- Evening, 1 hr — paper reading (slower mode)
- 1 hr — project work that counts toward the budget

**Weekend (~4 hrs/day, 2 days):**

**Friday review (30 min)** — write down what clicked, what didn't, queue questions for next week. Add unresolved items to `docs/learning-curriculum.md` as TODOs.

**Never skip:** Karpathy core videos (Weeks 1–2), Raschka Ch 4–7 (Weeks 3–4), LoRA + QLoRA papers, Anthropic *Contextual Retrieval*, your project work hours. These are load-bearing for the case study.
